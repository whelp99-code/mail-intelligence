# Mail Intelligence v1.2.0 — Precision Classification & Intelligent Exploration

- Status: APPROVED / IMPLEMENTATION BASELINE
- Date: 2026-08-30
- Worker: `mailintelligence`
- Depends on: v1.1.0 Persistent Mail Memory
- Safety boundary: read-only Outlook; no external mutation

## 1. Purpose

v1.2.0 improves classification accuracy without multiplying taxonomy or turning every sentence into a permanent business object.

The governing principle is:

> Prefer a small, mutually exclusive decision surface with explicit uncertainty over a large taxonomy that creates conflicts, duplicate work, and self-reinforcing garbage.

The version adds two capabilities:

1. **Precision Classification** — decide the minimum set of fields required for the user to act.
2. **Intelligent Exploration** — interpret practical work-oriented queries and combine structured filters with full-text evidence search.

## 2. Fixed product contract

Each message may have many observations, but only the following six decision fields form the current classification:

1. One current work state
2. One next actor
3. At most one primary confirmed project, otherwise candidate or unassigned
4. One priority plus an optional due expression
5. Exact evidence spans
6. Per-field confidence

Everything else is a supporting signal or candidate. It does not become confirmed work knowledge automatically.

## 3. Core classification values

### 3.1 Current work state

Exactly one value is allowed.

| Value | Meaning |
|---|---|
| `ACTION_REQUIRED` | We have a concrete action to perform. |
| `WAITING` | Another person, team, or prerequisite must act first. |
| `DECISION_REQUIRED` | A user decision or approval is required before progress. |
| `COMPLETED` | The current request or work represented by the message is complete. |
| `REFERENCE` | No follow-up action is required. |
| `REVIEW_REQUIRED` | Evidence is conflicting, insufficient, or ambiguous. |

Urgency is not a work state.

### 3.2 Next actor

Exactly one value is allowed.

| Value | Meaning |
|---|---|
| `ME` | The mailbox owner should act. |
| `INTERNAL_TEAM` | A colleague or internal team should act. |
| `EXTERNAL_PARTY` | Customer, vendor, manufacturer, or other external party should act. |
| `SHARED` | Coordinated action by internal and external parties is required. |
| `NONE` | No next action exists. |
| `UNKNOWN` | The actor cannot be resolved safely. |

### 3.3 Priority

Exactly one value is allowed.

`CRITICAL | HIGH | NORMAL | LOW`

Priority is derived from due state, incident/security language, commercial or customer impact, and certainty. It must not be inferred from Outlook importance alone.

### 3.4 Project resolution

A message may have:

- one `CONFIRMED` primary project from the approved project registry,
- one `CANDIDATE` project label that remains unconfirmed, or
- `UNASSIGNED` / `REVIEW_REQUIRED`.

A project is never created from one message automatically.

## 4. Supporting signals

Signals are multi-valued observations, not primary classifications:

- `DEADLINE`
- `AMOUNT`
- `QUOTATION_CONTRACT`
- `ATTACHMENT`
- `ATTACHMENT_MISSING`
- `SCHEDULE`
- `APPROVAL`
- `INCIDENT_SECURITY`

Signals may improve search and explanations but may not create projects, work items, decisions, schedules, or risks by themselves.

## 5. Anti-garbage rules

### PG-001 — fail open to review, never fail closed to a false fact

Ambiguous or conflicting evidence produces `REVIEW_REQUIRED`, `UNKNOWN`, or `UNASSIGNED`.

### PG-002 — one layer, one answer

Current state, next actor, primary project, and priority are each single-valued.

### PG-003 — current clause outranks quoted history

Quoted messages, signatures, forwarded headers, and historical completion statements are excluded from current-state classification.

### PG-004 — observation is not knowledge

Rule or model findings are stored as observations/candidates. Only user-confirmed or policy-qualified values enter the current classification.

### PG-005 — user corrections outrank automation

A user correction remains authoritative until explicitly changed. Reclassification may update supporting evidence but may not overwrite corrected decision fields.

### PG-006 — no automatic project creation

Only explicit user/API project registration creates a project. Classification can only link to an existing active project or produce an unconfirmed candidate label.

### PG-007 — no duplicate event noise

Classification history is appended only when the stable classification fingerprint changes.

### PG-008 — no hidden AI fallback

Rule, AI, cache, and fallback sources are recorded. Invalid model output cannot modify the precision classification.

## 7. Data model

Migration 004 introduces:

### `projects`

Explicitly registered project records only.

- `project_key`
- `name`
- `aliases_json`
- `status`
- timestamps

### `precision_classifications`

One current classification per message.

- current work state
- next actor
- priority
- due raw/normalized values
- primary project or candidate label
- project resolution
- signals
- evidence by field
- confidence by field
- review reasons
- source/model/version
- stable fingerprint
- review status
- timestamps

### `precision_classification_events`

Append-only fingerprint changes for audit and learning.

### `precision_corrections`

One current user override per message plus an event trail. Nullable fields mean “do not override this field”.

### `precision_correction_events`

Append-only user corrections.

No work-item, decision, schedule, commitment, risk, or document object is auto-created in v1.2.0.

## 8. Processing flow

```text
Message revision
→ strip quote/signature history
→ deterministic observations
→ project registry matching
→ conflict/uncertainty evaluation
→ precision classification candidate
→ apply existing user correction
→ persist current classification
→ append event only when fingerprint changed
→ expose explanation and search facets
```

AI enhancement is optional and must pass its schema/evidence contract. The deterministic precision classifier remains available offline.

## 9. API surface

Read APIs:

- `GET /api/intelligence/summary`
- `GET /api/intelligence/search?q=...&limit=...`
- `GET /api/intelligence/projects`
- `GET /api/intelligence/classification?messageId=...`
- `GET /api/intelligence/smart-views`

Local protected writes:

- `POST /api/intelligence/classify`
- `POST /api/intelligence/projects`
- `POST /api/intelligence/correct`

None of these APIs mutate Outlook or another external system.

## 12. Acceptance gates

The version is complete only when:

1. `npm run verify:v1.2.0` exits 0.
2. All precision fixtures pass with no forced classification where review is required.
3. A fresh v1.1.0-format DB migrates to the new schema without data loss.
4. User corrections survive automated reclassification and service restart.
5. Intelligent search returns structured explanations and excludes deleted messages.
6. Project creation remains explicit and duplicate-safe.
7. Existing v1.1.0 read-only safety contract remains intact.
8. Ubuntu service is reloaded/restarted and live local checks pass.
9. Runtime secrets remain protected and no external mail mutation occurs.
10. Actual Outlook validation is reported separately if credentials are unavailable.

## 13. Explicit non-goals

- automatic project creation
- automatic work-item creation
- project merge/split automation
- autonomous email sending
- calendar/CRM/project-system writes
- unrestricted open-ended taxonomy
- graph database introduction
- vector search as source of truth
- model fine-tuning
- claiming continuous learning before correction outcome data exists
