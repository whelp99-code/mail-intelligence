# 판단 근거·대안·위험

[확인] 기존 발송 경로 테스트 26개와 Gateway 테스트 16개는 통과했다. [문서] Graph 소형 첨부·Drive 읽기/내보내기는 공식 API로 제공된다(01 출처). [추정] 2MiB 제한의 암호화 DB 사본 방식이 초기 운영 범위에 맞는지는 부하·백업 복원 시험으로 확인해야 한다.

선정 기준은 기존 승인 무결성, 최소 외부 권한, 복원 가능성, 구현 범위다. 탈락 조건은 첨부 변경을 승인 없이 허용하거나 키 없는 복원을 성공으로 표시하는 경우다.

| 대안 | 해결 범위 | 제약 | 조건부 판정 |
|---|---|---|---|
| 현행 유지 | 본문 전용 | 실제 첨부 요구 미해결 | 새 기능 게이트 실패 시 운영 유지 |
| 부분 수정: 링크만 | Drive 링크 전달 | 수신자 권한 미확인·사본 보장 없음 | F3만 독립 검증·승인되면 별도 활성화 가능 |
| 소형 사본+선택 Drive | F1~F7 | scanner·OAuth·DB 증가 | 복원·승인·실파일 검증 통과 시 초기 채택 후보 |
| 대용량 upload session | 큰 파일 | Mail.ReadWrite 확대·외부 초안 상태 추가 | 07 별도 승인과 게이트 전에는 실행 안 함 |

반론 1: DB에 파일을 넣으면 백업 크기와 잠금 시간이 증가한다. 우리 기존 SQLite 단일 DB 운영과 충돌할 수 있다. 512MiB 상한·짧은 트랜잭션·복원/부하 시험으로 검증하며 실패하면 별도 파일 저장소를 새 검토안으로 작성한다. 자동 교체하지 않는다.

반론 2: drive.file은 선택 범위가 좁지만 scope 자체에 쓰기 권한도 포함한다. 제품 코드의 읽기 전용 allowlist와 negative 테스트가 필요하다. 전체 Drive 검색을 위해 drive.readonly로 자동 확대하지 않는다.

반론 3: malware 검사 성공도 파일이 무해하다는 보증은 아니다. “검사 통과”만 표시하고 안전 보증 문구를 쓰지 않는다. 지원 형식 검사기가 없으면 해당 형식을 차단한다.

| 위험 | 초기 P×I×D(1~5)·등급 | 방어·검증 | 잔여 조건 |
|---|---|---|---|
| 승인과 다른 파일 발송 | 3×5×4=60 R4 | v2 digest·불변 자산·동일 버퍼 발송·변조 테스트 | 테스트 실패 시 release 금지 |
| 타 메일함 bytes 유출 | 3×5×4=60 R4 | mailbox/source 소유권·bot 다운로드 금지 | 교차 계정 synthetic 시험 필수 |
| OAuth 비밀·파일 로그 노출 | 3×5×3=45 R4 | 암호화·redaction·no-store·로그 검사 | 실제 토큰으로 테스트 로그 생성 금지 |
| 중복 발송 | 2×5×4=40 R4 | 기존 claim·무재시도·read reconcile | provider 불확실은 수동 조사 |
| DB 용량/복원 장애 | 3×4×3=36 R3 | quota·dry-run·별도 키 복구 | 운영 키 백업 승인 필요 |
| 변환 서식 손실 | 3×3×2=18 R2 | 사용자 다운로드 검토·원본 형식 선택 | 자동 품질 보증 금지 |

등급은 40 이상 R4, 20~39 R3, 10~19 R2, 나머지 R1인 계획용 우선순위이며 측정 사고 확률이 아니다. 잔여 위험 점수는 실제 시험 전 산정하지 않는다.

## 자율 실행 경계

Cursor 구현 요청을 받으면 로컬 소스·합성 테스트까지 진행할 수 있다. 운영 OAuth 등록/로그인, scanner 설치, migration 운영 적용, 토큰 scope 확대, commit/push/deploy, 실메일 발송, 보존 삭제는 별도 명시 승인 대상이다. 기존 승인된 text-only 테스트는 새 파일 전송 승인이 아니다.

조건부 결론: 승인 무결성·교차 계정 격리·백업 복원·첨부 수신 hash가 확인되면 소형 사본안을 활성화 후보로 올린다. 하나라도 실패하면 본문 전용 또는 검증된 링크 기능을 유지한다. DB 시험이 실패하거나 대용량이 필수로 확정되면 저장소/전송 선택을 재검토한다.
