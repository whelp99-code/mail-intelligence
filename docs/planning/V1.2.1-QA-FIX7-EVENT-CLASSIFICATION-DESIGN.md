- 비목표: 메일 자동 발송, 원본 변경, 프로젝트 자동 생성, 회사·제목·hash별 예외 추가

## 2. 문제 정의

qa-fix6는 알려진 두 회귀 세트 100건을 모두 맞췄지만 신규 Blind 50건에서는 다음 결과를 기록했다.

```text
Work State                 66.0%
Next Actor                 66.0%
Priority                   84.0%
Reference false-action      2.0%
Important Priority Miss     5.56%
Important Action Miss      44.44%
검색                         13/15
```

운영·안전·Evidence 기반은 통과했으므로 병목은 저장소나 OAuth가 아니라 메일 의미를 상태로 변환하는 구조였다.

기존 구조의 주요 한계:

1. 요청·완료·전달·대기 표현을 독립 정규식이 경쟁했다.
2. 자동 알림을 광고와 업무 알림으로 충분히 구분하지 못했다.
3. Support 티켓의 종료, 종료 승인, 일정, 파일 전달을 같은 문구 수준에서 처리했다.
4. 발신 메일의 `전달 완료`와 `상대방 확인 대기`가 흔들렸다.
5. Disclaimer와 조건부 문의 Footer가 Priority와 Action 근거를 오염시켰다.
6. 새 실패 사례를 정규식으로 추가할수록 알려진 표본에 과적합될 위험이 있었다.

## 3. 고정 원칙

### 3.1 상태 집합은 유지한다

```text
ACTION_REQUIRED
WAITING
DECISION_REQUIRED
COMPLETED
REFERENCE
REVIEW_REQUIRED
```

### 3.2 다음 행동 주체 집합도 유지한다

```text
ME
INTERNAL_TEAM
EXTERNAL_PARTY
SHARED
NONE
UNKNOWN
```

### 3.3 판단 순서

```text
INGEST
→ NORMALIZE
→ CURRENT/HISTORY SPLIT
→ DIRECTION/LIFECYCLE
→ EVENT EXTRACTION
→ EVENT PRECEDENCE
→ STATE/ACTOR/PRIORITY DECISION
→ EVIDENCE SPAN VALIDATION
→ CONFLICT/CONFIDENCE CHECK
→ STORE
→ USER CORRECTION OVERRIDE
```

### 3.4 금지 원칙

- 특정 message hash 예외 금지
- 특정 고객·회사명만을 위한 상태 예외 금지
- 제목 전체 문자열 고정 예외 금지
- 과거 인용문을 현재 Action 또는 Priority 근거로 사용 금지
- OAuth 또는 LLM 성공을 분류 정답으로 간주 금지
- 불확실한 결과를 억지로 Action으로 확정 금지

## 4. Event Frame

`src/domain/mail-event-extractor.js`는 정규화된 현재 본문에서 업무 사건을 먼저 추출한다.

Event Frame 구조:

```text
version
context
  direction
  lifecycle
  automated
candidates[]
  type
  rank
  confidence
  decision
  evidence
  attributes
primaryEvent
conflicts[]
```

Event는 특정 문장을 바로 상태로 바꾸는 단순 키워드 규칙이 아니다. 방향·폴더·자동화 유형·현재 본문 의미를 함께 사용해 후보 사건을 만들고, 우선순위 표에서 하나의 현재 상태를 선택한다.

## 6. 핵심 의미 경계

### 6.1 서비스 비활성화와 Marketing 구독 해지

```text
서비스·계정·업무 구독 비활성화 예정
→ ACTION_REQUIRED / ME

뉴스레터·마케팅 수신 거부
→ REFERENCE / NONE / LOW
```

두 경우 모두 `subscription`, `deactivate`, `unsubscribe`가 나타날 수 있으므로 현재 서비스 연속성 영향과 Marketing 문맥을 함께 검사한다.

### 6.2 Support 티켓

```text
문제가 해결됐고 티켓을 종료한다
→ COMPLETED

해결 여부와 종료 승인을 묻는다
→ ACTION_REQUIRED / ME

내일 지원 일정을 확정했다
→ WAITING / EXTERNAL_PARTY

패치·로그·파일을 전달했다
→ COMPLETED
```

`추가 문의가 있으면 회신하십시오`는 Footer이며 독립 Action이 아니다.

### 6.3 발신 메일

```text
견적서·제안서·답변만 전달
→ COMPLETED / NONE

전달 후 확인·검토·회신을 요청
→ WAITING / EXTERNAL_PARTY

상대방에게 자료·견적·처리를 직접 요청
→ WAITING / EXTERNAL_PARTY

조건부 미래 제안
예: 필요하면 말씀 주시면 전달하겠습니다
→ 현재 Action으로 승격하지 않음
```

### 6.4 세금계산서·청구서

```text
자동 청구서 준비 + 보기 링크 + 자동 결제 설명
→ REFERENCE / LOW

전자세금계산서 제목의 source→target이 수신자 방향
→ REVIEW_REQUIRED / NORMAL

발행자 관점의 보관·확인 기록
→ REFERENCE / LOW

실제 발행·제출·회신 요청
→ ACTION_REQUIRED
```

전자세금계산서 제목의 `outer(source->target)` 관계를 정규화해 방향을 판단한다. 회사명 자체는 상태 예외로 사용하지 않는다.

### 6.5 공유 폴더 인증

```text
폴더가 공유됐고 이메일 인증이 필요함
→ ACTION_REQUIRED / ME
```

단순 공유 알림과 실제 접근을 위한 인증 필요를 분리한다.

### 6.6 Priority

`HIGH`는 현재 본문의 검증 가능한 긴급 근거가 있을 때만 허용한다.

```text
금일 해결 필요
오늘·내일 처리
빠른 조치
즉시 대응
```

`CRITICAL`은 현재 보안·장애·서비스 중단과 긴급·즉시 근거가 함께 있을 때만 허용한다.

다음은 Priority 근거로 사용하지 않는다.

- Disclaimer
- 기밀 고지
- 잘못 수신한 경우 삭제 안내
- 조건부 문의 Footer
- 과거 전달·인용 본문
- `importance=high` 단독
- 계약·견적 키워드 단독

## 7. Conflict 처리

비슷한 우선순위의 Event가 서로 다른 Work State를 요구하면 `conflicts[]`에 기록한다.

현재 정책:

1. 명시적 lifecycle·Support·서비스 연속성 사건은 일반 문구보다 우선한다.
2. 동일 우선순위에서 실제 충돌하고 확신이 낮으면 `REVIEW_REQUIRED`로 내려갈 수 있다.
3. Event가 없으면 기존 정밀 분류 규칙을 fallback으로 사용한다.
4. 사용자 보정은 Event와 자동 분류보다 항상 우선한다.

## 8. Evidence 계약

Event의 Evidence도 기존 exact span 계약을 사용한다.

```text
sourceField
sourceMessageId
startOffset
endOffset
exactText
sourceHash
normalizationVersion=exact-source-span-v1
```

저장 조건:

```text
canonicalSource.slice(startOffset, endOffset) === exactText
sha256(canonicalSource) === sourceHash
```

현재 본문에서 검증되지 않는 Event는 자동 확정에 사용하지 않는다.

보안 단일 검색은 다음 중 하나가 없는 VPN-only 결과를 제거한다.

## 10. Ground Truth 계약

기존 150건은 회귀용이다.

```text
Round 3 고정 50
qa-fix5 Blind 고정 50
qa-fix6 Blind 고정 50
```

Ground Truth consistency audit에서 의미적으로 동일한 Template에 상충 라벨이 발견되면 라벨을 수정하지 않는다. 해당 세트는 report-only로 보존하고, 최종 릴리스는 새로운 Blind Holdout이 결정한다.

qa-fix7 평가 계약:

```text
important-priority-and-action-v3

Important Priority Miss:
important=true
AND expected.priority != LOW
AND actual.priority = LOW

Important Action Miss:
expected.workState is actionable
AND actual.workState is not actionable
```

`important=true + expected.priority=LOW` 라벨은 경고와 legacy 진단으로 남기되 Priority Miss 분모에는 포함하지 않는다.
