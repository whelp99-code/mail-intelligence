## 3. 고정 운영 정책

### 3.1 Lifecycle

```text
삭제·정크 폴더
→ 현재 Action 생성 금지
→ REFERENCE / NONE / LOW

최근의 불완전한 삭제 Draft
→ REVIEW_REQUIRED / UNKNOWN / NORMAL

현재 Draft의 실질 요청
→ 발송 대기 업무
→ WAITING / EXTERNAL_PARTY
```

삭제·정크 메일은 기록과 검색 이력으로는 보존하지만 현재 업무 Inbox로 다시 올리지 않는다.

### 3.2 방향과 다음 행동 주체

```text
내가 보낸 요청
→ WAITING / EXTERNAL_PARTY

내가 자료·답변만 전달
→ COMPLETED / NONE

내가 전달하고 상대 확인·회신을 요청
→ WAITING / EXTERNAL_PARTY

상대가 나에게 현재 행동을 요청
→ ACTION_REQUIRED / ME

상대가 외부 Support 주소에 요청하고 내가 참조됨
→ WAITING / EXTERNAL_PARTY
```

방향은 sender 하나만 보지 않고 sentitems 폴더, mailbox sender alias, 수신자 역할을 함께 사용한다.

### 3.7 Priority

HIGH 이상은 현재 본문의 검증 가능한 근거에만 연결한다.

```text

- 현재의 긴급·즉시·금일·오늘·내일
- 48시간 이내 명시 기한
- 카드·쿼터 초과 위험
- 라이선스 invalid/expired로 현재 업무 중단 위험

CRITICAL
- 실제 서비스 중단
- 보안 침해·랜섬웨어·치명적 active incident
```

### MI #93: 긴 질문 분해 (intelligent-search-v1.2.2-fix13)

10단어를 초과하는 질문은 기존 구조화 필터를 원문에서 파싱한 뒤,
명시적인 한영 질문 상용구만 제거하여 식별어·키워드로 분해한다.
분해 여부·키워드 한도·정확 일치는 동일한 NFKC Unicode letter/mark/number 및 하이픈/밑줄 토큰화를 사용한다.
쉼표 등 구두점으로 나열한 11개 의미 키워드도 거부하며, 정확히 10개는 유지한다.
알 수 없는 업무 용어는 유지하며, 의미 있는 키워드가 10개를 초과하면
잘라서 검색하지 않고 `no_safe_result`로 중단한다. 정보 없는 질문도 전체 메일
검색으로 바꾸지 않는다. 문자 500자 제한, FTS 최대 12개, 기존 coverage 기준,
메일함·삭제·정크·프로젝트·기한·보안 필터와 의미 근거 검증은 유지한다.
분해된 발주번호 및 숫자 식별어(예: `EPO2609-164`, `49725`)는 coverage 재시도에서도 필수 anchor다.
숫자만 있는 참조는 기존 `49725` 사례에 근거하여 5자리 이상을 기본 기준으로 삼는다.
더 짧은 숫자는 invoice/order/ticket/quote 또는 인보이스/주문/티켓/견적 등의 바로 인접한 참조 문맥이 있어야 한다.
명시적인 금액·통화·소수 및 날짜/기간은 숫자 참조로 승격하지 않는다. 같은 숫자가 명시적 참조와 금액으로 모두 쓰이면 참조 가드는 유지한다.
식별어 anchor를 먼저 추가하여 기존 anchored coverage(50%)를 계산한다. anchor 없는 60% 기준은 그대로다.
SQLite의 deterministic 함수는 binding된 식별어를 동일 Unicode 토큰의 대소문자 무시 정확 일치로 검사한다.
부분 문자열이나 긴 번호 prefix는 허용하지 않는다. 한글·결합문자 인접은 경계가 아니며 구두점은 경계다.
식별어/lexical coverage는 FTS가 색인하는 `sender_email`과 `sender_name`도 대조한다.
명시적인 `from 주소`는 정규화된 발신자 주소 전체를 binding하여 정확 일치로 제한한다. 주소 내부는 업무 키워드나 조사로 재해석하지 않는다.
숫자 뒤 조사는 공용 `CONTROL_PARTICLE_SUFFIXES` 목록으로만 정규화하며 `로/만/도`와 조합을 지원한다. 영문 접미사는 자르지 않는다.
날짜/기간 단위(`년/월/일/주/분기/개월` 및 한정 접미사)는 식별어로 취급하지 않는다.
기존 날짜 파서가 선택·검증한 기한 표현만 lexical 조건에서 소비하고 `due_date` 메타데이터 필터로 검증한다.
Unicode 식별어 내부의 `EPO-2026-13-10` 같은 날짜 모양 부분문자열은 날짜 후보에서 제외한다. 독립된 잘못된 기한은 계속 거부한다.
해석되지 않은 기간은 원문 키워드로 유지하며 임의의 기간 범위로 바꾸거나 삭제하지 않는다.
이때 coverage 재시도는 비활성화하여 기간 조건이 선택적 검색어로 약화되지 않게 한다.
긴 질문의 잘못된 기한 날짜는 coverage 재시도로 필터를 우회하지 않고 fail-closed 처리한다.
`recognized.queryDecomposition`은 `keywords` 또는 `refused`로 노출된다.

`the N most recent`, `latest/top N`, `최근 N건/최신 N개`의 첫 명시적 수량은 `limitHint`로만 소비한다.
수량 질문은 짧아도 상용구 분해를 적용한다. 인용된 프로젝트명·실제 참조번호·금액·날짜는 수량으로 바꾸지 않는다.
기존 `boundedLimit` 검증을 재사용하며 양의 정수만 적용하고 최대 100 및 호출자의 limit보다 늘리지 않는다. 0/음수/소수는 호출자의 검증된 limit로 돌아간다.
수량만 있고 업무 근거나 구조화 필터가 없는 질문은 여전히 `no_safe_result`다. 의미 키워드 10개 한도는 그대로다.

### MI #95: 검색 후속 일관성 수정 (intelligent-search-v1.2.2-fix14)

- 선택한 기한은 `intentQuery`의 정확한 span 위치로 먼저 제거한다. 동일 날짜가 포함된 식별어는 보존하고, 다른 치환과 수량 제거 전에 공백 마스킹으로 위치를 유지한다. 날짜의 일(day) 부분은 뒤따르는 `latest`의 수량으로 재해석하지 않는다.
- 유효한 기한이 선택되어도 다른 기한 후보의 `invalidDate`를 유지한다. 분해 질의는 후보 순서와 관계없이 fail-closed다.
- 유효한 양의 정수 `latest N` / `N most recent` / `최근 N건` / `최신 N개`는 `sortOrder=date_desc`다. SQL LIMIT 전에 수신일(없으면 발신일, 최초 저장일) 내림차순, 동률은 내부 메시지 ID 내림차순으로 정렬한다. 의미 근거 필터는 유지하되 재순위가 날짜순을 바꾸지 않는다. coverage 재시도도 같다. `top N`과 잘못된 수량은 기존 관련도순이다.
- 발신자 주소 전체의 대소문자 비교는 SQLite ASCII `LOWER` 대신 동일 JavaScript 정규화를 양쪽에 적용한다. 메일함·삭제·정크 제한과 전체 주소 정확 일치는 유지한다.
- 저장 토큰과 질의 식별어는 공용 `normalizeIntelligentSearchToken`으로 조사 조합을 정규화한 뒤 정확 일치한다. 더 긴 번호·알 수 없는 접미사·인접 Unicode 식별어는 일치시키지 않는다.

