## 배포 중 발견·수정한 문제

### 1. 접근키 배포의 UI 변경 요청 헤더

접근키가 활성화된 서버는 로컬 상태 변경 요청에 `X-Mail-Intelligence-Request: 1`을 요구하지만 프런트엔드는 CSRF 헤더만 전송하고 있었다. 설정 저장, Delta 동기화, 백업 버튼이 실제 배포에서 거부될 수 있었다.

수정:

```text
모든 비 GET/HEAD UI 요청
→ X-CSRF-Token
→ X-Mail-Intelligence-Request: 1
```

외부 행동 권한은 추가하지 않았다.

### 2. 실행 중 서비스와 격리 Health 검증 포트 충돌

실서비스가 3010을 사용하면 `verify:health:full`이 격리 서버 대신 실서비스를 검사할 수 있었다.

수정:

```text
명시적 PORT가 없을 때
→ 사용 가능한 loopback 포트 자동 할당
→ 격리 서버 기동
→ 중복 기동 검사
```

실서비스 실행 중에도 전체 릴리스 게이트가 통과한다.

### 3. 사용자 systemd 호환 하드닝

일부 capability 기반 systemd 하드닝 옵션은 사용자 서비스에서 `218/CAPABILITIES`로 실패했다. 사용자 서비스에서 지원되는 범위로 조정했다.

유지한 보호:

```text
NoNewPrivileges
PrivateTmp
ProtectSystem=full
ProtectHome=read-only
ReadWritePaths=data/
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
UMask=0077
```

애플리케이션 자체의 loopback·세션·CSRF·읽기 전용 Scope·Kill Switch는 그대로 유지한다.

## 실제 Outlook 파일럿이 아직 실행되지 않은 이유

Ubuntu 환경에서 다음이 모두 없는 것을 확인했다.

```text
Microsoft/Outlook 환경변수
기존 Outlook 공개 설정
Client ID
Tenant 설정
Mailbox 설정
OAuth Token
```

따라서 실제 메일함 접속을 임의로 수행할 수 없다. 다음 단계는 사용자가 브라우저에서 Microsoft 로그인과 `Mail.Read` 동의를 완료하는 것이다.

## 접속

Mac에서:

```bash
ssh -N -L 3010:127.0.0.1:3010 jm@jm-acloud
```

브라우저:

```text
http://127.0.0.1:3010
```

Basic 인증:

```text
사용자: mailintelligence
비밀번호 확인:
ssh jm@jm-acloud 'cat /home/jm/orca/projects/mail-intelligence/data/.mail-intelligence-access-key'
```

로그인 후 `Outlook 연결 설정`에서 Client ID를 넣고 Microsoft 로그인을 완료해야 실제 Delta 동기화 검증을 진행할 수 있다.
