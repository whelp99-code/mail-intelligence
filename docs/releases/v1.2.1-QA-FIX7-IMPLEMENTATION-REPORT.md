## 1. 해결 목표

qa-fix6의 신규 Blind 50건은 Work State 66%, Next Actor 66%, Priority 84%, Important Action Miss 44.44%로 실패했다. 알려진 문구를 정규식으로 추가하는 방식의 과적합을 중단하고, 현재 메일의 의미 사건을 먼저 추출한 뒤 상태를 결정하도록 구조를 변경했다.

```text

→ DIRECTION / LIFECYCLE / AUTOMATION
→ SEMANTIC EVENT FRAME
→ STATE / NEXT ACTOR / PRIORITY
→ CONFLICT REVIEW
→ EXACT EVIDENCE
```

## 2. qa-fix7 구조

### 2.1 Semantic Event Frame

신규 모듈:

```text
src/domain/mail-event-extractor.js
```

현재 제목·현재 본문·메일 방향·폴더 lifecycle·자동 발신 정보를 입력받아 다음 사건을 구분한다.

```text
support_completed
support_close_approval
support_schedule_confirmed
support_information_request
service_deactivation_warning
quota_or_card_limit_risk
subscription_followup_required
shared_access_verification
new_tax_invoice_review
invoice_confirmation_reference
billing_notice_reference
outgoing_delivery_completed
outgoing_delivery_waiting
outgoing_answer_completed
incoming_direct_question
active_incident_action
current_action_urgency
```

각 사건은 다음 계약을 가진다.

```text
type
precedence
confidence
workState
nextActor
priority
evidence
```

분류기는 가장 강한 사건을 선택하고, 동일 우선순위에서 서로 다른 상태가 충돌하면 자동 확정하지 않고 `REVIEW_REQUIRED`로 보낸다.

### 2.2 Support lifecycle

```text
문제 해결·티켓 종료 통보
→ COMPLETED / NONE

해결됐으니 종료해도 되는지 승인 요청
→ ACTION_REQUIRED / ME

상대방이 지원 일정을 확정
→ WAITING / EXTERNAL_PARTY

로그·자료를 요청
→ ACTION_REQUIRED / ME
```

`추가 문의가 있으면 회신하세요` 같은 조건부 Footer는 현재 업무로 승격하지 않는다.

### 2.3 서비스·결제·접근 사건

```text
서비스 비활성화 예정
→ ACTION_REQUIRED / ME / NORMAL

카드 한도·쿼터 초과 위험
→ ACTION_REQUIRED / ME

구독 신청 후 추가 절차 필요
→ ACTION_REQUIRED / ME

공유 폴더·파일 접근을 위한 이메일 인증
→ ACTION_REQUIRED / ME

마케팅 수신 거부 문구
→ REFERENCE / NONE / LOW
```

### 2.4 청구서·세금계산서

```text
전자세금계산서 신규 도착·검토 필요
→ REVIEW_REQUIRED / UNKNOWN / NORMAL

Bill36524 확인 완료·보관 알림
→ REFERENCE / NONE / LOW

일반 청구서 준비 알림
→ REFERENCE / NONE / LOW

실제 발행·회신·처리 요청
→ ACTION_REQUIRED / ME
```

동일 Microsoft 청구서 템플릿에 대해 qa-fix5와 qa-fix6 동결 Ground Truth가 서로 다른 라벨을 갖는 충돌을 발견했다. 라벨은 변경하지 않았으며 consistency audit에서 명시적으로 보고한다. 이 충돌 세트는 release gate가 아니라 report-only 회귀로 취급한다.

### 2.5 발신 메일

```text
자료·답변·산출물만 전달
→ COMPLETED / NONE

전달 후 수신자의 확인·승인·회신 요청
→ WAITING / EXTERNAL_PARTY

상대방에게 자료·견적·답변을 요청
→ WAITING / EXTERNAL_PARTY
```

조건부 도움말 Footer만으로 WAITING을 만들지 않는다.

### 2.6 Priority

HIGH·CRITICAL은 현재 본문에서 검증되는 근거만 사용한다.

```text
HIGH
- 금일·오늘·내일 등 현재의 근접 기한
- 현재의 명시적 긴급 요청
- 서비스 비활성화·한도 초과 등 직접 위험

CRITICAL
- 현재 발생 중인 보안 침해·서비스 중단
- 즉각 복구가 필요한 active incident
```

다음은 Priority 근거에서 배제한다.

```text
과거 인용문
법적 Disclaimer
조건부 문의 Footer
Outlook importance 단독 신호
일반 계약·견적 단어
```

## 14. 남은 Release Gate

Aside가 다음을 독립 수행해야 한다.

```text
1. 검증 대상 source snapshot 동결
2. 신규 Main Blind 50건 예측 비노출 라벨링
3. Incident/security 5건 예측 비노출 라벨링
4. 라벨 파일 0400 + SHA-256 동결
5. 최초 채점
6. Work State / Next Actor / Priority >=95%
7. Reference false-action <=2%
8. Important Priority/Action Miss <=3%
9. 검색 15개 독립 relevance >=90%
10. Evidence 100%
11. Delta 2회
12. 백업·격리 복원
13. 재시작
14. 30분 안정성
15. 안전선 위반 0
```

Aside가 GO를 내린 뒤에만 Commit·Push와 정식 운영 승격을 결정한다.
