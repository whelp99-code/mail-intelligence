## 2. qa-fix3 분류 수정

### 2.1 사용자 발신 주소 학습과 custom folder 방향 판정

운영 DB의 mailbox key는 이메일 주소가 아니라 `me`였다. 기존 분류기는 표준 `보낸 편지함`만 outgoing으로 보고, 사용자가 보낸 메일이 custom folder로 이동하면 incoming처럼 판단할 수 있었다.

수정:

```text
보낸 편지함 또는 Draft의 sender email
→ mailbox sender alias로 학습
→ 같은 sender의 custom-folder 메일도 outgoing으로 판정
```

정책:

```text
보낸 실제 요청
→ WAITING / EXTERNAL_PARTY

보낸 자료·견적 전달
→ WAITING / EXTERNAL_PARTY

Draft
→ 아직 발송되지 않았으므로 ACTION_REQUIRED / ME 유지
```

운영 alias:

```text
발견된 사용자 발신 alias: 1개
own-sender ACTION_REQUIRED/ME 위반: 0
outgoing WAITING actor 위반: 0
```

### 2.2 전달·완료·검토 요청 분리

다음을 별도 의미로 분리했다.

```text
재견적·견적서·발주서·장비 정보 전달
+ 새 요청 없음
→ COMPLETED / NONE

문서 전달
+ 별도 문장의 “확인/검토 부탁드립니다”
→ ACTION_REQUIRED / ME

전자서명 문서 최종 완료 알림
→ COMPLETED / NONE

보낸 인사말·서명만 존재
→ REFERENCE / NONE
```

### 2.3 자동 문서·세금계산서 알림

다음 Ecount·자동 문서 패턴은 사용자 업무로 승격하지 않는다.

```text
수신문서보기
이카운트에서 보낸 메일
EFFICIENT CHANGE
loginaa.ecount.com
resourcev3.ecount.com
```

자동 알림은:

```text
REFERENCE / NONE / LOW
```

실제 발주서·세금계산서 발행·검수 요청은 계속 Action으로 유지한다.

### 2.4 정보성 thread update

다음과 같이 혼선을 막기 위해 본문을 정리·수정했다는 통보는 새 업무가 아니다.

```text
내용 혼선 방지 위해 본문 메일에 수정 게시 합니다.
```

결과:

```text
REFERENCE / NONE / NORMAL
```

### 2.5 직접 연락처·이메일 요청

다른 이메일 주소나 연락처를 달라는 실제 요청을 Action으로 인식하도록 action object를 확장했다.

```text
다른 메일이나 연락처 부탁드립니다.
→ ACTION_REQUIRED / ME
```

### 2.6 Priority 계약

기존의 모든 Reference/Completed 일괄 LOW 정책을 제거했다.

```text
광고·뉴스레터·자동 알림·삭제·정크
→ LOW

업무 참고 정보
→ NORMAL

Outlook 중요도 HIGH인 업무 참고 정보
→ HIGH

업무 완료 통보
→ NORMAL

본문에 명시적 업무가 두 개 이상
→ HIGH
```

따라서 중요한 완료·참고 업무가 무조건 LOW로 내려가는 문제를 줄였다.

## 3. qa-fix3 검색 수정

`장애`·`보안` 검색은 더 이상 넓은 FTS 동의어만으로 Top-5를 채우지 않는다.

### 3.1 장애 검색

다음 중 하나를 요구한다.

```text
제목의 장애·오류·중단·접속불가·outage·incident
incident_security 구조화 signal
Work State exact Evidence의 장애 문맥
```

### 3.2 보안 검색

다음 중 하나를 요구한다.

```text
제목의 보안·security·침해·해킹·랜섬웨어·취약점·breach·malware
incident_security 구조화 signal
Work State exact Evidence의 보안 문맥
VPN + 문제 문맥이 같은 제목 또는 같은 Evidence에 함께 존재
```

### 3.3 억제 대상

```text
광고
세금계산서 폴더
보험·청약서
일반 VPN 임대 계약 완료
삭제·정크
서명·FAQ에만 존재하는 단어
서로 다른 Evidence field를 잘못 합친 cross-field match
```

운영 검색 스모크:

```text
10개 동일 질의 deterministic gate PASS
장애 결과 3건, incident noise 0
보안 결과 3건, security noise 0
보험·일반 계약 garbage 0
invoice-folder garbage 0
promotional 0
lifecycle garbage 0
```

이 값은 개발자 deterministic gate이며 독립 Top-5 relevance 점수를 대체하지 않는다.

## 4. Provider 건강 상태 보정

안전 운영에서 `MAIL_INTELLIGENCE_ALLOW_EXTERNAL_AI=0`인 상태로 AI 분석 버튼이나 검증 경로가 호출되면, 실제 Provider 장애가 아닌 운영 정책 차단이다.

수정:

```text
EXTERNAL_AI_DISABLED
EXTERNAL_AI_OPT_IN_REQUIRED
```

은 Provider 실제 건강 실패 이벤트로 기록하지 않는다. 사용자에게는 Rules fallback과 운영 정책 비활성 상태를 설명한다.

이 정책 차단이 마지막 실제 Luna 성공 상태를 실패로 덮어쓰는 회귀를 차단하는 테스트를 추가했다.

실제 Provider 네트워크 재호출은 실행 도구의 별도 외부 네트워크 승인 때문에 이번 수정 세션에서는 수행하지 못했다. Round 2 독립 QA에서 OpenAI Luna 합성 및 실메일 분석은 실제 PASS했고, qa-fix3은 Provider 실행 어댑터가 아니라 상태 기록 정책만 변경했다.
