# Mail Intelligence v1.2.0 구현 보고서

- 버전: `1.2.0`
- 릴리스명: `Precision Classification & Intelligent Exploration`
- 작업자: `mailintelligence`
- 기준 계획: `docs/planning/V1.2.0-PRECISION-CLASSIFICATION-PLAN.md`
- 안전 기준: Outlook 읽기 전용, 외부 변경 기능 비활성화
- Git commit / push: 수행하지 않음

## 1. 목적

v1.2.0의 목적은 분류 항목을 계속 늘리는 것이 아니라, 사용자가 실제로 행동하는 데 필요한 최소 항목을 정확하게 판단하는 것이다.

```text
세분화 최대화                 X
모든 문장의 업무 객체화       X
낮은 신뢰도 추론의 사실 승격  X

현재 업무 상태 1개            O
다음 행동 주체 1개            O
주 프로젝트 최대 1개          O
우선순위·기한                 O
원문 근거                     O
필드별 신뢰도                 O
애매하면 검토 필요로 보류      O
```

## 2. 핵심 분류 계약

### 현재 업무 상태

```text
action_required\waiting
decision_required
completed
reference
review_required
```

### 다음 행동 주체

```text
me
internal_team
external_party
shared
none
unknown
```

### 프로젝트 해석

```text
confirmed       사용자가 등록한 프로젝트의 정확한 이름·별칭 하나와 일치
candidate       등록되지 않은 프로젝트형 표현
unassigned      연결 근거 없음
review_required 여러 등록 프로젝트가 동시에 일치
```

프로젝트는 메일 분석으로 자동 생성하지 않는다.

### 보조 신호

```text
deadline
amount
quotation_contract
attachment
attachment_missing
schedule
approval
incident_security
```

보조 신호는 검색과 설명에 사용하지만 독립적인 업무·결정·위험 객체를 자동 생성하지 않는다.

## 3. 구현 내역

### SQLite schema v4

Migration `004_precision_classification.sql`을 추가했다.

```text
projects
precision_classifications
precision_classification_events
precision_corrections
precision_correction_events
```

주요 보장:

- 한 메일의 현재 정밀 분류는 하나만 유지
- stable fingerprint가 바뀐 경우에만 변경 이벤트 추가
- 사용자 보정은 별도 current/event 구조로 저장
- 프로젝트 이름·별칭 중복 차단
- 프로젝트 생성은 명시적 로컬 API로만 허용
- 기존 v1.1.0 메일·스레드·보정·분석 데이터 보존

### 정밀 분류 엔진

`src/domain/precision-classifier.js`를 추가했다.

- 현재 본문과 인용된 과거 메일 분리
- 서명과 전달 헤더 제외
- 구체적 요청과 “확인 바랍니다” 같은 모호한 문구 구분
- 현재 요청이 과거 완료 표현보다 우선
- 결정·승인 요청 분리
- 내부/외부 대기 주체 분리
- 발신 방향을 이용한 다음 행동 주체 판단
- KST 기준 명시·상대 기한 정규화
- Outlook importance만으로 긴급 처리하지 않음
- 정확한 프로젝트 별칭 하나만 연결
- 충돌·불확실성은 강제 확정하지 않음
- 필드별 근거·신뢰도 저장

### 지능형 탐색

`src/domain/intelligent-search.js`를 추가했다.

## 4. Anti-garbage 동작

1. 한 분류 층에는 하나의 답만 허용한다.
2. 불확실하면 `review_required`, `unknown`, `unassigned`를 사용한다.
3. 프로젝트는 사용자 등록 전까지 후보에 머문다.
4. 같은 프로젝트명·별칭은 중복 등록할 수 없다.
5. 한 메일을 매번 재분류해도 fingerprint가 같으면 이벤트를 추가하지 않는다.
6. 사용자 보정은 자동 재분류와 재시작 후에도 유지한다.
7. 보조 신호는 정식 업무 객체를 만들지 않는다.
8. 삭제된 메일은 지능형 탐색 결과에서 제외한다.
9. AI 출력은 기존 스키마·근거 검증을 통과해야 하며 자동 분류를 조용히 덮어쓰지 않는다.

## 7. 최종 검증 상태

최종 릴리스 게이트와 Ubuntu 재배포 증거는 작업 완료 시 본 문서와 체크리스트에 확정 기록한다.

현재 개발 원칙상 다음을 별도로 구분한다.

```text
v1.2.0 엔지니어링 게이트   검증 진행
실제 Outlook read-only pilot  Microsoft OAuth 자격정보가 있을 때 별도 검증
외부 행동                   NO-GO
```

## 8. 제한 사항

- 실제 회사 Outlook 메일함 분류 정확도는 사용자 OAuth 연결과 평가 표본이 필요하다.
- 사용자 보정 데이터를 모으기 전에는 지속 학습이 완료됐다고 주장하지 않는다.
- 프로젝트는 명시적 등록 방식이며 자동 프로젝트 생성은 의도적으로 지원하지 않는다.
- 자동 WorkItem·Decision·Schedule·Risk 객체 생성은 v1.2.0 범위가 아니다.
- 벡터 검색과 그래프 DB는 도입하지 않았다.
